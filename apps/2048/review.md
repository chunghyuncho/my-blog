# 2048 게임 — Review 결과

## 발견한 문제와 수정 내역

**코드 자체에서 수정이 필요한 버그는 발견되지 않았습니다.**

검증 과정에서 일시적으로 이상 동작(점수/타일 수가 예상과 다르게 증가)이 관찰되었으나, 원인을 추적한 결과 이는 브라우저 자동화 도구(Browser pane)의 `navigate` 액션이 동일 URL로 재이동할 때 페이지를 완전히 새로 로드하지 않고 이전 JS 실행 컨텍스트(bfcache 유사 동작)를 유지하거나, 물리적 키 입력 이벤트가 지연 전달되는 테스트 환경/도구 특성 때문이었습니다. 캐시버스팅 쿼리 파라미터로 진짜 새 로드를 강제하거나 `dispatchEvent`로 순수 JS 레벨 검증을 수행한 결과, 실제 게임 코드에는 해당 문제가 없음을 확인했습니다(즉, 실제 사용자가 새 탭에서 페이지를 열 때는 재현되지 않는 테스트 도구의 특성이며 애플리케이션 결함이 아닙니다).

이에 따라 `apps/2048/` 폴더 내 파일은 전혀 수정하지 않았습니다.

## 남은 이슈나 한계

- **승리(2048) 오버레이는 실제 브라우저에서 2048 타일까지 도달시켜 육안으로 확인하지는 못했습니다.** 자동화된 휴리스틱 봇 여러 종류(코너 우선순위 이동, 매 수마다 빈 칸이 최대가 되는 방향 선택)를 동원했으나 세션 시간 내에 2048 타일 생성에 이르지 못했습니다(2048 게임 자체의 난이도 문제로, 최적 알고리즘 없이는 흔한 결과입니다). 대신 관련 코드(`script.js` 176~210번 줄의 병합·승리 판정 로직)를 정밀 트레이스하여 로직 정확성을 코드 리뷰 수준에서 확인했으며, 이미 실기 검증된 게임오버 오버레이와 동일한 `showOverlay()` 함수/포커스 이동/입력 차단 메커니즘을 그대로 공유하므로 실질적 리스크는 낮다고 판단합니다. 필요 시 별도로 `Math.random`을 고정하거나 임시 테스트 훅을 넣어 강제로 승리 시나리오를 재현하는 후속 검증을 권장할 수 있습니다.
- 그 외 스와이프의 실제 손가락 제스처(물리 터치스크린) 검증은 불가능한 환경이라 `Touch`/`TouchEvent` API를 이용한 시뮬레이션으로 대체했습니다. 로직 자체가 키보드 이동과 동일한 내부 함수를 공유하므로 실질적 차이는 없을 것으로 판단합니다.

## 최종 결론

**Embed(블로그에 카드 추가) 단계로 진행해도 좋습니다.**

핵심 로직(이동/병합/랜덤 타일/점수/최고점수 저장), UI/UX(반응형 레이아웃, 애니메이션, 오버레이), 접근성(포커스 관리, aria 속성, 키보드 전용 플레이) 모두 spec.md 요구사항을 충족하며, 실기 테스트에서 콘솔 에러나 기능적 결함이 발견되지 않았습니다. 승리 오버레이만 실제 트리거를 통한 육안 확인이 남아있으나 코드 로직상 결함 가능성은 낮아 Embed 진행을 막을 사유는 아닙니다.
